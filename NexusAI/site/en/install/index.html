Installation guide

Install NexusAI step by step.

NexusAI has two parts: the plugin, installed in Moodle, and your own server that searches the material and talks to the AI. This guide installs both, connects them and gets the assistant ready to use in your courses.

Before you start

You will need:

  • Moodle 4.5 to 5.3, with a site administrator account.
  • A Linux machine for the NexusAI server, with internet access. It can be the Moodle machine or another one.
  • An API key from an AI provider compatible with the OpenAI API. Gemini has a free tier: get the key at Google AI Studio.
  • If Moodle will reach the server over the internet: a domain or subdomain pointing to that machine.

Only the Moodle server talks to the NexusAI server. Students' browsers never connect to it directly, so it does not need to be open to everyone.

1Install the server

The server runs in Docker from a prebuilt image, so there is nothing to compile. It is four containers: the NexusAI API, PostgreSQL with pgvector (the database and the material index), Redis and, if you use HTTPS, Caddy. Everything comes from the nexusai-backend repository.

1.1 The machine

  • System: Linux. The commands in this guide are for Ubuntu or Debian.
  • Memory: a small machine is enough. Our servers have 1 GB of RAM.
  • Disk: the first start downloads about 1.5 GB of images. After that it grows with the material teachers upload (up to 20 MB per file).
  • Network: outgoing internet access, to talk to the AI provider. With HTTPS, also ports 80 and 443 open to the machine; in a cloud, open them in the provider's network rules too.

1.2 Install Docker

If the machine does not have Docker, the official script installs Docker and Docker Compose:

curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER

The second command lets you run docker without sudo. Log out and back in for it to take effect. To check:

docker compose version

It should show version 2 or later.

1.3 Download the files

git clone https://github.com/nexusai-ucc/nexusai-backend.git
cd nexusai-backend
cp .env.example .env

From here on, run every command inside the nexusai-backend folder. The file that starts everything is docker-compose.selfhost.yml, and .env already selects it, so plain docker compose is enough.

1.4 Configure .env

First generate two random values: one for the API key and one for the shared secret. Run this command twice and copy each result:

openssl rand -hex 32

Then open .env (for example with nano .env) and replace the example values. It ends up like this:

COMPOSE_FILE=docker-compose.selfhost.yml
ENV=production

LLM_API_KEY=AIzaSy...your-gemini-key
EMBEDDING_API_KEY=AIzaSy...your-gemini-key

NEXUSAI_API_KEY=3f9c1e...the-first-openssl-value
NEXUSAI_SHARED_SECRET=a71e0b...the-second-openssl-value

POSTGRES_USER=nexusai
POSTGRES_PASSWORD=any-long-password

API_PORT=8001
VariableWhat it is
LLM_API_KEYThe key of the AI provider that answers the questions.
EMBEDDING_API_KEYThe key used to index the material. With Gemini, the same as the one above.
NEXUSAI_API_KEYThe first generated value. It also goes in Moodle, in step 3.
NEXUSAI_SHARED_SECRETThe second generated value. It also goes in Moodle.
POSTGRES_PASSWORDThe database password. It is only used inside Docker, so any value works.
API_PORTThe port on the machine where the API listens. Change it if 8001 is taken.

Do not change POSTGRES_PASSWORD after the first start. The database is created with that password: if you change it in .env, the API can no longer connect.

1.5 Choose how Moodle reaches it

It depends on where Moodle is:

  • Same machine or same internal network. Nothing else is needed. In step 3, the server URL is http://machine-ip:8001, or http://localhost:8001 on the same machine.
  • Over the internet. Use HTTPS, so questions and material travel encrypted. Create a DNS A record pointing your domain (for example nexusai.your-institution.edu) to the machine's public IP, and add at the end of .env:
COMPOSE_PROFILES=https
NEXUSAI_DOMAIN=nexusai.your-institution.edu
API_BIND=127.0.0.1

COMPOSE_PROFILES=https adds Caddy, which gets and renews the HTTPS certificate on its own. API_BIND=127.0.0.1 keeps port 8001 closed to the outside, so the only way in is HTTPS. In step 3, the server URL is https://nexusai.your-institution.edu.

Want to try it without your own domain? nip.io builds one from the IP: NEXUSAI_DOMAIN=nexusai.203.0.113.10.nip.io (use the machine's public IP instead of those numbers). Fine for testing, not for real use. If your institution already has a proxy (nginx, Apache), skip Caddy: keep API_BIND=127.0.0.1 and point the proxy to http://127.0.0.1:8001.

1.6 Start and check

docker compose up -d

The first time it downloads the images and creates the database, so it takes a few minutes; after that it starts in seconds. To see the status:

docker compose ps

api, postgres and redis should be Up and (healthy), and caddy Up if you use HTTPS. uploads-init shows as exited: that is normal, it only prepares the material folder and stops. Test the API:

curl http://localhost:8001/health

With HTTPS, test it from outside too: curl https://nexusai.your-institution.edu/health. It should answer something like:

{"status":"ok","version":"0.1.0","env":"production","llm_model":"gemini-3.5-flash"}

If it does not answer, check the log with docker compose logs api and look for your case in Troubleshooting.

1.7 Keep it running

See what is going on. The API log, live (exit with Ctrl+C):

docker compose logs -f api

Update to the latest version. Database changes are applied automatically on start:

git pull
docker compose pull
docker compose up -d

Make a backup. The database and the original files of the material:

docker compose exec -T postgres pg_dump -U nexusai nexusai > nexusai-$(date +%F).sql
docker compose cp api:/app/uploads ./uploads-$(date +%F)

Keep those copies off the machine. To schedule them, add them to crontab -e.

Restore a backup. This replaces the current database with the backup (change the file name):

docker compose stop api
docker compose exec -T postgres dropdb -U nexusai nexusai
docker compose exec -T postgres createdb -U nexusai nexusai
docker compose exec -T postgres psql -U nexusai nexusai < nexusai-2026-11-26.sql
docker compose cp ./uploads-2026-11-26/. api:/app/uploads
docker compose up -d

Shut it down. docker compose down stops everything and keeps the data. docker compose up -d starts it again.

Do not use docker compose down -v unless you want to delete everything: -v removes the database and the material.

2Install the plugin

  1. Download the .zip from the Moodle Marketplace.
  2. In Moodle, go to Site administration → Plugins → Install plugins.
  3. Upload the file and follow the installer to the end.

If your Moodle does not allow installing from the web, unzip the .zip into local/nexusai (on Moodle 5.1 or later, public/local/nexusai) and go to Site administration → Notifications.

3Connect them

In Site administration → Plugins → Local plugins → NexusAI settings, section Backend connection:

FieldValue
Backend API URLThe one you chose in step 1.5: https://nexusai.your-institution.edu or http://machine-ip:8001
API keyThe value of NEXUSAI_API_KEY
Shared secret (HMAC)The value of NEXUSAI_SHARED_SECRET

Save the changes and purge the caches in Site administration → Development → Purge caches.

Keep both keys safe. With them, anyone can ask the server for anything on behalf of any user. Do not send them by email or commit them to a repository.

4Check the connection

Open Local plugins → NexusAI · Admin panel (or the /local/nexusai/admin.php address of your Moodle). The panel queries the server and shows whether it answers, its version and how long it takes.

If it shows an error, look for your case in Troubleshooting.

5Turn NexusAI on in courses

NexusAI ships turned off in every course, so you can turn it on one course at a time. There are three ways:

  • The teacher, from the course. In the course menu (sometimes under “More”), open NexusAI in this course, tick Use NexusAI in this course and save. Editing teachers and managers can do it.
  • In every course at once. In NexusAI settings, tick On by default in courses. It applies to courses without their own setting.
  • From the command line, in the Moodle folder:
php local/nexusai/cli/enable_course.php --courseid=12
php local/nexusai/cli/enable_course.php --list   # which courses have it on

Once the course is on, the teacher uploads the material and students can start using it. The tutorial shows how.

On the server

Add them to the server's .env. After changing it, apply it with docker compose up -d --force-recreate api.

What forVariables
Use another AI provider to answerLLM_BASE_URL, LLM_MODEL and LLM_API_KEY. For example, for OpenAI: LLM_BASE_URL=https://api.openai.com/v1 and LLM_MODEL=gpt-4o-mini. The material can keep being indexed with Gemini.

Troubleshooting

The admin panel cannot connect to the server

The Moodle server cannot reach the NexusAI server. From the Moodle server, try curl with the URL you entered plus /health. If it does not answer, check that the domain points to the right machine and that no firewall blocks the port (443 with HTTPS, 8001 without). If outgoing traffic goes through a proxy, set it in Site administration → Server → HTTP.

Authentication error (401)

The API key or the shared secret in Moodle does not match the ones in .env: check that no extra space was pasted. It also happens when the two servers' clocks differ by more than 5 minutes: turn on time sync (NTP) on both.

The assistant does not show up in the course

Check that NexusAI is on in that course (step 5) and that Enable NexusAI is ticked in the settings. Then purge the caches. The user also needs the local/nexusai:use capability, which students and teachers have by default.

It says it cannot find the answer in the material

The file may not have finished indexing: in NexusAI · Materials it has to show as indexed. NexusAI also only answers with material each student can see: if the activity is hidden or restricted, it does not exist for that student.

The API does not start or keeps restarting

Check the log with docker compose logs api. The usual causes: an example value is still in .env (REPLACE_ME); POSTGRES_PASSWORD was changed after the first start; or API_PORT is not a number (the address goes in API_BIND). If the error says port is already allocated, the port is taken: change API_PORT.

Caddy cannot get the HTTPS certificate

Check docker compose logs caddy. To get the certificate, the domain must already point to the machine's public IP (a new DNS record can take a while to propagate) and ports 80 and 443 must be open, in the cloud network rules too. Caddy retries on its own.

The chat answers with an error

It is usually the AI provider: the key is wrong or the quota ran out. Gemini's free tier has a daily request limit. The details are in docker compose logs api.
